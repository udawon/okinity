# 낚시 투어 상세 — 클래스 선택 상단 재배치 및 내용 전환 구조

- 작성일: 2026-08-29
- 대상 브랜치: feat/tour-photo-gallery (또는 신규 브랜치)
- 요청: 상품 페이지 진입 시 상단에서 미들클래스/럭셔리클래스를 먼저 선택하게 하고, 선택에 따라 본문 내용이 전환되도록 재설계

## 1. 현황 분석

### 1.1 현재 페이지 구조 (운영 확인: /ko/tours/trial-fishing-4h)

렌더 순서 (`src/app/[locale]/tours/[slug]/page.tsx:96-183`):

1. ← 카테고리 링크
2. 투어 사진 캐러셀 (`TourPhotoCarousel`, 공통)
3. 헤더: 킥커 / 제목 / 요약
4. 메타 행: 소요 + **가격("미들클래스 : 100,000엔 / 럭셔리클래스 : 200,000엔" 단일 문자열)** — `page.tsx:91-94`
5. 포함 사항 (공통)
6. 본문 (공통)
7. **클래스 탭 (`TourClassTabs`) — 페이지 최하단.** 미들/럭셔리 탭 전환 시 요트 사진 1장 + 스펙 설명만 바뀜 — `page.tsx:161-173`
8. 예약 문의 CTA (`/reserve?tour={slug}`)

### 1.2 데이터 소스

| 데이터 | 저장 위치 | 비고 |
|---|---|---|
| 투어 상세(summary·price·included·body·images) | site_content `tour:{slug}` (+`:en`/`:ja`) | 스키마 `src/lib/tour.ts:105-114` |
| 클래스(미들/럭셔리) 사진·스펙 | site_content `fishing_classes` (+`:en`/`:ja`) **낚시 4종 공통 단일 키** | `src/lib/tour.ts:79-98` |
| 가격 | `tour:{slug}.price` **자유 텍스트 1개** — 클래스별 분리 없음 | `src/lib/tour.ts:110` |

- 클래스 탭 노출 판정: `tourHasClasses(slug)` = fishing 카테고리 4종 전부 (`src/lib/tour.ts:67-69`)
- 예약 폼(`src/components/ReservationForm.tsx:55`)에는 낚시 클래스 선택 상태(`fishingClass`)가 이미 존재하나, 상세 페이지에서 클래스 정보가 전달되지 않아 사용자가 폼에서 다시 골라야 함.
- `ReservePlanner.tsx:35`는 `searchParams.get('tour')`만 읽음 — `class` 파라미터는 없음.

### 1.3 운영 DB 현재 상태 (2026-08-29 조회)

- `fishing_classes` 존재: middle=YANMAR EX-46 사진+스펙, luxury=URATA UR-70 사진+스펙. `:en`/`:ja` 키도 존재.
- `tour:fishing-5species-6h`, `tour:overnight-fishing` 키 부재(미작성·비공개) — 이 두 페이지는 기본 정보 + 클래스 탭 + CTA만 노출 중.

## 2. 문제 정의

1. **선택 동선 역전**: 구매 결정에 가장 중요한 변수(클래스=배 등급, 가격 2배 차이)가 페이지 최하단에 있어, 방문자가 공통 설명을 다 읽은 뒤에야 클래스 개념을 만난다.
2. **가격 정보가 전환에 반응하지 않음**: 가격이 단일 문자열이라 클래스를 골라도 "내가 고른 클래스의 가격"이 강조되지 않는다.
3. **예약 단절**: 상세에서 클래스를 보고 넘어가도 예약 폼에서 클래스를 다시 선택해야 한다.

## 3. 해결 방안

### 결정 A — 클래스별 가격 데이터 모델

#### A-1. `priceMiddle`/`priceLuxury` 필드 추가 (권장)
- `TourDetailSchema`에 `priceMiddle: z.string().default('')`, `priceLuxury: z.string().default('')` 추가.
- 표시 규칙: 선택 클래스의 가격이 있으면 그것을 표시, 두 필드 모두 비면 기존 `price` 문자열을 폴백으로 고정 표시(전환 없음).
- 어드민 `TourEditor`: 낚시 투어(`tourHasClasses`)일 때만 두 입력칸 추가. 기존 `price` 칸은 "클래스 없는 투어용/폴백" 안내와 함께 유지.
- 장점: DB 마이그레이션 0건(zod default), 하위호환 완전, 언어별 키(:en/:ja) 흐름 그대로 상속.
- 단점: 배포 후 어드민에서 낚시 4종 × 언어별 가격 입력이라는 운영 후속 작업 발생.
- 추천도: 상

#### A-2. 가격은 그대로 두고 사진/스펙만 전환
- 데이터 변경 0. 구현 최소.
- 단점: "선택에 따라 내용이 바뀐다"는 요구의 핵심(가격)이 빠진 반쪽 구현. 추후 재작업 확실.
- 추천도: 중

#### A-3. 기존 `price` 문자열을 정규식으로 파싱해 분리
- 자유 텍스트("미들클래스 : 100,000엔 / …") 파싱은 형식 변경에 취약, 언어별 표기 상이. **기각.**
- 추천도: 하

### 결정 B — 상태 관리/렌더링 구조

#### B-1. 클라이언트 래퍼 + 서버 children (권장)
- 새 클라이언트 컴포넌트(가칭 `TourClassExperience`)가 선택 상태를 소유하고, 다음을 렌더:
  1. 클래스 선택 세그먼트(상단, 버튼에 클래스명+가격 병기)
  2. 메타 행(소요 + 선택 클래스 가격)
  3. 클래스 요트 사진+스펙(전환)
  4. `children` — 포함 사항·본문(서버 렌더 그대로 주입)
  5. 예약 CTA(`?tour={slug}&class={선택}`)
- `TourClassTabs.tsx`는 이 컴포넌트로 대체. 비낚시 투어는 기존 렌더 경로 그대로(픽셀 동일).
- 장점: 서버 컴포넌트 이점(본문 SSR) 유지, 상태 한 곳, 전환 즉시(왕복 없음).
- 단점: `page.tsx`의 낚시/비낚시 분기가 커짐(낚시일 때 메타·CTA를 래퍼 안으로 이동).
- 추천도: 상

#### B-2. URL 쿼리(`?class=`) + 서버 렌더
- 공유 가능한 URL, JS 없이 동작.
- 단점: 페이지가 `force-dynamic`이라 토글마다 서버 왕복 → 체감 느림, 스크롤 유지 처리 필요. 2옵션 토글에 과한 비용.
- 추천도: 하

### 결정 C — 진입 시 기본 선택

#### C-1. 미들 클래스 기본 선택 (권장)
- 현 탭 기본값과 동일. 진입 즉시 완결된 화면. SSR 초기 화면 = 미들이라 깜빡임 없음.
- 단점: "선택을 먼저 하게 만든다"를 문자 그대로(강제 선택) 원했다면 미충족.
- 추천도: 상

#### C-2. 강제 선택 (선택 전 클래스 종속 영역을 안내 문구로 가림)
- 선택 의도가 명확해지고 클래스 인지율 100%.
- 단점: 클릭 1회의 마찰, 첫 화면에 가격·배 정보 공백, 이탈 리스크.
- 추천도: 중

### 결정 D — 예약 폼 클래스 연동

#### D-1. CTA에 `&class={선택}` 전달 (권장)
- `ReservePlanner.tsx`: `searchParams.get('class')` 읽어 `initialClass`로 전달. `ReservationForm.tsx`: `fishingClass` 초기값으로 사용(낚시일 때만, 'middle'/'luxury' 외 값은 무시).
- 변경 2파일 소폭. 상세→예약 클래스 재선택 마찰 제거.
- 추천도: 상

#### D-2. 미연동 (현행 유지)
- 폼에 이미 클래스 드롭다운이 있으므로 기능 자체는 동작. 다만 재선택 마찰 유지.
- 추천도: 중

## 4. 트레이드오프 분석 (권장 조합 A-1+B-1+C-1+D-1)

- **얻는 것**: 클래스 우선 동선, 가격·사진·스펙 동시 전환, 예약까지 클래스 연속성, DB 마이그레이션 0건, 비낚시 투어 무영향.
- **치르는 것**: 어드민 가격 입력 운영 작업(4종×3언어, 미입력 동안은 기존 문자열 폴백으로 안전), `page.tsx` 낚시 분기 복잡도 증가, 클래스 종속 영역의 클라이언트 컴포넌트화(번들 소폭 증가 — 기존 TourClassTabs도 클라이언트였으므로 증가폭 미미).
- **바꾸지 않는 것(명시)**: 클래스 사진/스펙이 낚시 4종 공통(`fishing_classes` 단일 키)이라는 정책, 투어 사진 캐러셀(ko 키 단일 관리), SEO 메타데이터 생성 경로, 비공개 투어의 노출 규칙(클래스 영역은 공개 여부 무관 상시 노출 — 기존 `page.tsx:161` 주석과 동일).

## 5. 권장 사항

**A-1 + B-1 + C-1 + D-1.** 근거: 요구의 핵심이 "선택이 내용(특히 가격)을 바꾼다"이므로 가격 분리(A-1)는 필수에 가깝고, B-1은 기존 아키텍처(서버 컴포넌트 + 클라이언트 섬) 관례를 유지하는 최소 변경이며, C-1/D-1은 이탈 없이 전환 경험을 완성한다.
